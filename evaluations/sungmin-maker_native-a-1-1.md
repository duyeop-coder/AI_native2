## 항목 3. 핵심 기술 원리 적용 — PASS

| # | 세부 항목 | 근거 | 인터뷰 확인 포인트 |
|---|---|---|---|
| 1 | 리스트·딕셔너리 선택 이유 | 리스트: 등록 순서 유지 + 번호(인덱스) 접근. 딕셔너리: 필드 이름으로 의미 있게 접근, 필드 추가가 쉬움 | 리스트는 제목으로 찾을 때 전체 순회(O(n))가 필요하다는 단점, 제목을 키로 하는 딕셔너리를 쓰지 않은 이유(제목 중복 가능) |
| 2 | `while` 메뉴 반복과 종료 조건 | `main()`의 `while True` + `"0"` 입력 시 `break`. `KeyboardInterrupt`/`EOFError`도 종료로 처리 | 반복 횟수를 미리 알 수 없어서 `for`가 아닌 `while`을 쓴 이유 |
| 3 | "제목 또는 내용 포함" 구현 | `keyword in prompt["title"].lower() or keyword in prompt["content"].lower()` — `in` 연산자 + `or`, 양쪽 `lower()`로 대소문자 무시 | `or` 대신 `and`였다면 결과가 어떻게 달라지는지, 한글에는 `lower()`가 영향 없음 |
| 4 | 브랜치 분리 이유와 병합 기준 | `feature/prompt-list`에서 목록 기능 개발 → 동작 확인 후 머지 커밋으로 병합 | 병합 시점 기준(기능 완료 + 실행 확인). 단, 브랜치를 **목록 기능 1개에만** 사용했으므로 다른 기능은 왜 바로 커밋했는지 질문 권장 |

## 총평

필수 기능은 모두 정상 동작하고, 입력 검증과 예외 처리가 꼼꼼합니다. `find_prompts(prompts, condition)`로 조회·검색·즐겨찾기의 필터 로직을 하나로 합치고 전체 목록 기준 번호를 유지한 점, 카테고리를 상수 한 곳에서 관리하고 직접 입력한 카테고리를 조회에 자동 반영한 점이 설계상 강점입니다. 기본 데이터로 이전 미션의 실제 프롬프트를 넣어 과제 맥락을 살린 점도 좋습니다.

보완할 점은 다음과 같습니다.
1. Git 사용자 정보와 커밋 작성자가 본인이 아닌 `Claude`로 되어 있습니다. 본인 이름·이메일로 설정해야 합니다.
2. 브랜치를 목록 기능 1개에만 사용했습니다. 기능마다 브랜치를 나누고 병합하는 흐름을 더 보여주면 좋습니다.
3. 보너스 과제(JSON 영속화, 수정/삭제, 조회수)는 진행하지 않았습니다.
